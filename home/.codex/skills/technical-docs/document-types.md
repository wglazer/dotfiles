# Document types

Treat these as content choices, not mandatory headings. Omit anything irrelevant; do not add empty sections, generic risks, or boilerplate to look complete.

1. **Design doc or RFC:** State the proposed decision and why it is needed. Establish the problem, success criteria, and constraints. Explain the design so each choice follows from those premises. Include a representative request or event when it clarifies behavior. Compare credible alternatives against the same criteria when the choice needs justification, including keeping the current system when viable. Explain material failures, operational costs, validation, and rollout where relevant. Surface unresolved decisions rather than writing around them. Keep the reasoning that determines the choice in the main text; move derivations and exhaustive schemas to an appendix that readers can skip.
2. **How-to or README:** Optimize for the first successful use: purpose, prerequisites, a working path, and an expected result. Keep optional configurations and edge cases out of that path. Separate teaching a newcomer, completing a task, explaining a concept, and looking up exact behavior when combining them would obscure the reader's goal. Check commands and examples against the current project.
3. **Requirements:** Describe observable behavior rather than prescribing an implementation unless that implementation is a real constraint. Give each requirement one testable obligation. Define conditions, thresholds, tolerances, and failure behavior where needed; mark undecided values as unresolved. Use stable IDs only when traceability helps.
4. **Plan or issue:** Start with the question or outcome. Give actions, a concrete deliverable, and “Done when” checks. Include dependencies, estimates, and owners only when known and useful. Keep tasks small enough to execute and verify.
5. **Status update or technical explanation:** Answer the stakeholder's question first. State what changed or what is known, why it matters, and the next action or decision if one is needed. Keep completed work, expectations, and blockers distinct. Include implementation detail only when it helps the reader assess the result.
6. **PR description:** Use a short, action-led intent line, then one brief paragraph explaining the change and why it matters. Add at most 3–4 short `###` sections for meaningful details; use fewer when sufficient. Include relevant validation and material limitations without repeating the summary. Follow required repository templates and metadata.
7. **Commit message:** Follow established repository commit conventions. Otherwise use a concise Conventional Commit: `type(scope): short description`, omitting an unhelpful scope. Add a body when useful to explain the change.
