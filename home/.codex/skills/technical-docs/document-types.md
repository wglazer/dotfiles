# Document types

Treat these as content choices, not mandatory headings. Omit anything irrelevant; do not add empty sections, generic risks, or boilerplate to look complete.

1. **Design doc or RFC:** State the problem, proposed decision, and reasoning needed to assess it. Include constraints, success criteria, examples, alternatives, operational concerns, validation, or rollout only when they matter to the decision. Surface unresolved decisions. Keep essential reasoning in the main text; move lengthy supporting detail to an appendix when useful.
2. **How-to or README:** Optimize for the first successful use: purpose, prerequisites, a working path, and an expected result. Keep optional configurations and edge cases out of that path. Separate teaching a newcomer, completing a task, explaining a concept, and looking up exact behavior when combining them would obscure the reader's goal. Check commands and examples against the current project.
3. **Requirements:** Describe observable behavior rather than prescribing an implementation unless that implementation is a real constraint. Give each requirement one testable obligation. Define conditions, thresholds, tolerances, and failure behavior where needed; mark undecided values as unresolved. Use stable IDs only when traceability helps.
4. **Plan or issue:** Start with the question or outcome. Include actions, deliverables, completion criteria, dependencies, estimates, and owners when they help someone carry out or verify the work. Keep tasks small enough to execute.
5. **Status update or technical explanation:** Answer the stakeholder's question first. State what changed or what is known, why it matters, and the next action or decision if one is needed. Keep completed work, expectations, and blockers distinct. Include implementation detail only when it helps the reader assess the result.
6. **PR description:** Open with a single, concise sentence summarizing the change, with no heading. Add context and details only when they help a reviewer understand or assess the change. Use short sections only when they improve navigation; avoid formulaic sections such as Evidence or Merge danger. Report validation and limitations when they affect review or merging, with specific results and implications. For multi-step flows, use a readable numbered list or Mermaid diagram when it clarifies the relationships; avoid long arrow chains that wrap. Follow required repository templates and metadata.
7. **Commit message:** Follow established repository commit conventions. Otherwise use a concise, descriptive subject line. Add a body when useful to explain the change.
